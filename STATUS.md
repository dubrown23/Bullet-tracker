## Where we are

Bullet Tracker is a working personal habit app on SwiftData + CloudKit, brought up to the iPhone Duo and Apple's current design language over 2026-10-24/25 (`bt-0008` → `bt-0016`): iOS 26 target, size-class-aware layout, system chrome everywhere, the **week-grid** Today row, one **win rule**, a consistency pass, and a **tappable tile-grid widget** Dustin confirmed on his Duo.

On 2026-10-26/27 the long-planned merge with **Dustin's Health** went from design to live in three beads. The design (shared note `~/Desktop/Personal/dustin-system/memory/in_flight/habits-voice-dh-bullet-2026-10-26.md`): Dustin talks to Claude on his iPhone; voice lands in dustin-health (dh) as day facts + an inbox of actions; **Bullet pulls and grades everything itself**. `bt-0017` (Step 0) proved the pipeline with fake data. `bt-0018` (Step 2) added the rules: a neutral **Rest** grade, **targets as habit settings** with a stamped go-live day, **Today in progress**, and a **source** (auto / hand / voice) on every entry so hand grades win until "Back to Automatic", with **only the iPhone writing automatic grades**. **`bt-0019` (Step 3) is live:** the iPhone holds the app's key to dh in its Keychain and syncs on open and on pull-down; the real Diet and Workout are graded from real data from 2026-10-27 forward; the iPad never calls dh.

**`bt-0021` (2026-10-27 evening) made those two rows legible.** Dustin couldn't tell whether Diet or Workout was coloured by the app, by him or by voice, and the Workout form couldn't show what the sync had written. Now the Today caption leads with **Auto / Set by you / Set by voice** and carries a **Back to Auto** button on the row itself (he never found it in the long-press menu; he used the row button at once). Log Details is always offered for the two graded habits and leads with the mode, then **Meals from Dustin's Health** (one line per meal: time, name, calories · protein — dh now sends per-meal `items`) on Diet and **From Dustin's Health** sessions (minutes, set count, start) on Workout, with the type chips lit from dh's category. dh's lists live under a `health` key **inside the existing details text** (no schema change, old builds ignore it; the sync writes it only when it changed and never touches state, source or edit time). Passed on the simulator and on DBd with real data.

**`bt-0020` (2026-10-28) made hand taps reach dh by themselves.** Before, a tap only travelled on the next open or pull-down, so "what's left today" by voice could still list what Dustin had just tapped. Now every hand write on today (Today squares, Rest, Log Details, from one hook at the end of the three `HabitStore` writes) arms a **3 s timer**; each tap restarts it, so a burst is **one** send, and the send is the same full run as pull-down (`op=sync` goes first, so dh knows within about a second). Any run that starts for another reason drops the waiting timer. **Leaving the app** (lock, Home) with a tap waiting sends at once inside a background-task window taken at the tap, and two dates on disk (`tapWaitingSince`, `lastSentAt` = the start of the last run whose `op=sync` succeeded; the widget's own `lastWidgetUpdate` stamp joins the same check) make the next open sync **regardless of the 120 s throttle** — proven on the phone through an airplane-mode kill: the first open after relaunch read "open · tap waiting". iPhone + key only; the iPad schedules nothing. The Developer screen's Last run line now says **why** a run happened (open / open · tap waiting / pull-down / after a tap / leaving the app / Back to Auto / Settings / Developer) and counts runs since launch. The ds agent's code review before the phone pass caught Back to Auto running twice (the store's hand-off to the engine is a queued main-actor task, so a hand write followed at once by a forced run armed the timer after the run began); fixed, with a test proven to fail on the old line. 84 tests. Passed on the Duo simulator with the fake and on DBd with real data, seven checks, one action at a time.

Standing rule, in Dustin's words: **use Apple's guidelines whenever possible.** No one-offs: fix the pattern, not the instance. Pass tests force the failure state; they don't wait for it to happen by luck. Device pass tests are walked **one action at a time**: "Do: … / You should see: …", then wait. Put the common action **on the row**, visible; the long-press menu is the backup.

Harness facts worth knowing: Xcode 27 has no Simulator.app, the Duo simulator only shows the folded panel, so regular-width checks run on the iPad Air sim and the real look is checked on Dustin's devices (`DBd` iPhone, `Dustin's iPad (3)`). One device-interaction session at a time; check the run destination before any run (it has been his phone; it was switched back to the Duo simulator at the end of this session). The app target's folders are plain Xcode groups and a hook blocks direct `project.pbxproj` edits: create new files with `XcodeWrite` into an existing group and Xcode adds them to the target itself. **In-memory test stores must say `cloudKitDatabase: .none`** — on the iOS 27.1 simulator runtime the default picks up the iCloud entitlement and every save throws "No eligible connection available". **The full test plan runs the UI tests alongside the unit tests on the one simulator**, relaunching the app over and over, which bounces the unit-test host between background and active; `HabitSyncEngine.isUnderTest` therefore makes the host app's own on-open sync a no-op (only a test's `testOverride` drives a run), else the one-run-at-a-time guard swallows the tests' sends. The simulator ignores a synthesized power button, so lock-the-phone behaviour is proven on DBd only. When Dustin texts from the phone during a pass, every return to the app after two minutes is an "open" run that overwrites the Developer "Last run" line — have him read the line inside the app before switching away.
