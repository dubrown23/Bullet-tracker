# Pre-existing data integrity — HabitEntry records with null `completionState`

## Why

Surfaced 2026-05-14 during `bt-0005` Pile B verification run. When the app launches, the Xcode console floods with 100+ Core Data validation errors of the same shape:

```
Error Domain=NSCocoaErrorDomain Code=1570 "%{PROPERTY}@ is a required value."
entity: HabitEntry; NSValidationErrorKey=completionState; NSValidationErrorValue=null
```

And SwiftData's CloudKit mirror reports:

```
CoreData+CloudKit: <NSCloudKitMirroringDelegate> - Never successfully initialized
and cannot execute request '<NSCloudKitMirroringExportRequest>' due to error:
Multiple validation errors occurred.
```

What's happening: `bt-0003` Phase-2 migration collapsed completion state into a typed `CompletionState` enum and made it required (non-optional) on `HabitEntry`. The wipe + restore migration was supposed to ensure all entries had valid `completionState` values. Either the migration left some entries with `null` `completionState`, OR CloudKit pulled in old data from another device's store that pre-dates the migration. ~100 entry IDs visible in the error log (`p847` through `p981` range), suggesting a contiguous block of legacy entries.

The app **functions normally** — Today/Dashboard/Journal render + interact (verified during `bt-0005` simulator run). Only background CloudKit sync is choking. Nothing user-visible is broken.

This is **pre-existing**, not caused by `bt-0005` — first observed during the Pile B verification run, which was the first end-to-end app launch since the `bt-0003` ship on 2026-05-13. The errors have been silently failing CloudKit sync since the migration; they only became visible when Dustin ran the app for Pile B's verification gate.

## Out of scope

- Any `bt-0005` Pile B work (already shipped 2026-05-14).
- UI changes — the user-facing surface works fine; this is sync/data hygiene only.
- Schema shortcuts — making `completionState` (or any SwiftData attribute) optional without a proper `VersionedSchema` + `SchemaMigrationPlan` against the live CloudKit-synced container. 2026-05-14 first attempt did exactly this and broke sync; user-level memory `feedback_ios_real_fix` captures the lesson.

Two real candidate directions (don't commit to one without verification — that's what burned us on the first attempt):

- **(a) Real `VersionedSchema` migration.** Declare V1 (current shape: non-optional `CompletionState` backed by `INT64`) and V2 (target shape — optional, or different default, or whatever we settle on). Write a `SchemaMigrationPlan` mapping V1 → V2. Deploy the matching schema update to the CloudKit Dashboard for the dev container. Test the migration path against a real device with existing data. Substantial design surface; the right answer if we want to fundamentally change the field shape.

- **(b) CloudKit-side data cleanup, no schema change.** Find the ~100 null-`completionState` records in iCloud Dashboard (need to figure out how to query CD_HabitEntry past the `recordName not queryable` block — likely add a queryable index in dev schema, or use a record-name lookup if we can extract IDs from logs). Delete the bad records. Schema stays exactly as `bt-0003` left it. Smaller scope; doesn't fix the *class* of problem (any future records arriving with null can recreate the floor) but stops the bleeding.

Lean: (b) first, since it's reversible-via-restore and doesn't risk a repeat of the first attempt's schema-mismatch blowup. (a) only if (b) doesn't hold over time.

**Do not retry the one-line shortcut** (making `completionState` optional without a migration plan) — captured in user memory `feedback_ios_real_fix` as a hard rule.

## Decision log

- 2026-05-14 — first attempt **FAILED** + reverted same session. Plan claimed schema relaxation (`var completionState: CompletionState = .notDone` → `var completionState: CompletionState? = nil`) was a SwiftData lightweight migration needing no `VersionedSchema`. It wasn't. Build clean, simulator run produced **400+ sync failures per launch** (vs the original ~100 stuck records). The actual error past the `Unknown value class (__NSCFNumber)` flood:
  ```
  invalid attempt to set value type BYTES for field 'CD_completionState'
  for type 'CD_HabitEntry', defined to be: NUMBER_INT64
  ```
  What happened: SwiftData wrapped the new optional `CompletionState?` in a `NSCompositeAttributeDescription` locally (Apple's internal representation for optional `Codable`-enum-as-attribute), while CloudKit's container schema kept `CD_completionState` as `INT64` (the old non-optional shape). Local store wanted to send `BYTES`/dictionary; CloudKit container only accepts `NUMBER_INT64`. Every sync attempt rejected. State was strictly worse than the original problem because the schemas were no longer mutually compatible — not just a few stuck records but ALL writes failing.

  Reverted on 2026-05-14: `Data/Models.swift` field back to non-optional `CompletionState = .notDone`; `effectiveCompletionState` kept as a no-op pass-through (`var effectiveCompletionState: CompletionState { completionState }`) so the 13 read-site renames don't have to revert with the field. Local schema now matches CloudKit again; original ~100-record validation error flood returns, but that's the known floor we started from.

  **Lesson captured to user-level memory:** `~/.claude/projects/-Users-dbpro-Desktop-XCODE-Bullet-Tracker/memory/feedback_ios_real_fix.md` — in iOS on Apple's managed-object stacks (SwiftData / Core Data / CloudKit), apply the canonical Apple-blessed fix; never a shortcut. CloudKit's container schema is a separate registry from the local SQLite store and they must migrate in lockstep. "Lightweight migration" doesn't cover optionality changes when CloudKit is in the picture.

  **Next step (deferred):** the real fix is a `VersionedSchema` + `SchemaMigrationPlan` declaring V1 (non-optional `CompletionState`) → V2 (optional or whatever shape we settle on), plus a CloudKit Dashboard schema deploy to update `CD_completionState`'s server-side type. That's a substantial design surface — re-shape bt-0007 next session before any further attempt. Alternative: attack the problem from the cloud-cleanup side (delete the offending records via CloudKit Dashboard) and leave the schema untouched.
