# Pre-existing data integrity — HabitEntry records with null `completionState`

## Why

Surfaced 2026-05-14 during `bt-0005` Pile B verification run. When the app launches, the Xcode console floods with 100+ Core Data validation errors of the same shape:

```
Error Domain=NSCocoaErrorDomain Code=1570 "%{PROPERTY}@ is a required value."
entity: HabitEntry; NSValidationErrorKey=completionState; NSValidationErrorValue=null
```

And SwiftData's CloudKit mirror reports:

```
CoreData+CloudKit: <NSCloudKitMirroringDelegate> - Never successfully initialized
and cannot execute request '<NSCloudKitMirroringExportRequest>' due to error:
Multiple validation errors occurred.
```

What's happening: `bt-0003` Phase-2 migration collapsed completion state into a typed `CompletionState` enum and made it required (non-optional) on `HabitEntry`. The wipe + restore migration was supposed to ensure all entries had valid `completionState` values. Either the migration left some entries with `null` `completionState`, OR CloudKit pulled in old data from another device's store that pre-dates the migration. ~100 entry IDs visible in the error log (`p847` through `p981` range), suggesting a contiguous block of legacy entries.

The app **functions normally** — Today/Dashboard/Journal render + interact (verified during `bt-0005` simulator run). Only background CloudKit sync is choking. Nothing user-visible is broken.

This is **pre-existing**, not caused by `bt-0005` — first observed during the Pile B verification run, which was the first end-to-end app launch since the `bt-0003` ship on 2026-05-13. The errors have been silently failing CloudKit sync since the migration; they only became visible when Dustin ran the app for Pile B's verification gate.

## Out of scope

- Any `bt-0005` Pile B work (already shipped 2026-05-14).
- UI changes — the user-facing surface works fine; this is sync/data hygiene only.
- Schema shortcuts — making `completionState` (or any SwiftData attribute) optional without a proper `VersionedSchema` + `SchemaMigrationPlan` against the live CloudKit-synced container. 2026-05-14 first attempt did exactly this and broke sync; user-level memory `feedback_ios_real_fix` captures the lesson.

## Plan

**Shipped 2026-05-14 (second attempt — fix #2).** Option (c) — reset CloudKit Development environment via the CloudKit Developer Dashboard, let the app re-sync its clean local data back up. No schema change, no `VersionedSchema` work, no record-by-record query hunt.

**Why (c) over (a) or (b):** Dustin confirmed mid-session the historical habit data isn't vital — he's been using the app on and off for months, nothing critical to preserve. With that constraint relaxed:

- (a) `VersionedSchema` migration — overkill. The 100 broken records are migration garbage (residue from when CloudKit kept its old pre-`bt-0003` records after the wipe+restore brought local up to the new schema). No schema change is needed; the current non-optional shape is fine — we just need to clear the legacy null-state records.
- (b) Query + delete the 100 specific records — works but tedious (CloudKit needs queryable indexes; record names buried in error logs). No advantage over (c) since data preservation isn't a goal.
- (c) Reset Dev environment + re-sync from local — fastest. Cloud gets wiped clean; local (clean post-JSON-restore from last session's `bt-0007` failure recovery) re-uploads under the current schema; broken 100 gone, good records preserved.

**Steps executed:**

1. CloudKit Developer Dashboard → container `iCloud.db23.BulletTracker` → Development → Reset Environment → checkbox confirmed → Reset.
2. Force-quit Bullet Tracker on iPhone, reopened.
3. Tapped a habit completion to nudge a real local write → forced SwiftData's CloudKit mirror to push, triggering zone re-creation + schema auto-redeploy in the now-empty Dev environment.
4. Verified Xcode console after the clean re-launch: **no more** `NSValidationErrorKey=completionState`, **no more** `Never successfully initialized`, **no more** `invalid attempt to set value type BYTES`, **no more** `Zone Not Found`. Only normal sync chatter (`updateTaskRequest called for an already running task`, `WAL checkpoint`) and unrelated `NSKeyedUnarchiveFromData` deprecation noise remains.

**Future-proofing:** the source of the 100 records can't repeat — the current Swift model makes `completionState` non-optional, so the app literally cannot write null going forward. iPad already on the new schema (verified by `bt-0002`). No re-leak surface.

### Partial work already on disk from first-attempt revert

- `Data/Models.swift` has a no-op `effectiveCompletionState` accessor returning `completionState` directly.
- 12 files have `entry.completionState` → `entry.effectiveCompletionState` rename at 28 read sites. Functionally identical to the original — leave in place; if a future schema change makes the accessor non-trivial it's already plumbed, otherwise neutral and not worth a revert PR.

## Decision log

- 2026-05-14 — **second attempt SHIPPED** via option (c). Sequence: opened CloudKit Developer Dashboard → confirmed container `iCloud.db23.BulletTracker` was on Development environment → clicked "Reset Environment..." → confirmed "I understand all data in the development environment for this container will be permanently deleted" → clicked Reset. Force-quit app on iPhone, reopened. First re-launch surfaced expected post-reset `Zone Not Found (26/2036)` errors — CloudKit had wiped the zones, app's local sync state still expected them. Path forward: tap a habit to generate a real local write, which triggered SwiftData's CloudKit mirror to push, which triggered zone re-creation + schema auto-redeploy in the now-empty Dev environment. After Xcode console reset and clean re-launch verification: all four bug signatures gone (`NSValidationErrorKey=completionState`, `Never successfully initialized`, `invalid attempt to set value type BYTES`, `Zone Not Found`). Remaining console output is normal sync chatter (`updateTaskRequest called for an already running task` = CloudKit deduplicating overlapping export triggers; `WAL checkpoint: Database did checkpoint` = SQLite successfully flushing changes to disk) and one unrelated deprecation warning (`'NSKeyedUnarchiveFromData' will be removed in a future release` — Apple framework noise, separate watch-item, not blocking).

  **Key insight that unlocked the simpler fix:** Dustin's mid-session reframe — "data even if removed is not vital, I've been building it on and off and using it sparingly for months, but nothing is vital." This relaxed the data-preservation constraint that had been silently shaping the lean toward (b) over (a) in the original Plan. With historical data dispensable, (c) became obvious — reset Dev wipes ~all~ cloud-side records, but local clean copy re-seeds them on next sync. The 100 broken records were migration garbage (CloudKit kept its pre-`bt-0003` records when the local wipe+restore brought local up to the new schema), not ongoing leak — current non-optional Swift model can't write null records going forward, iPad already on new schema, no re-leak surface.

  **Why (c) wasn't on the candidate list when the bead was first shaped:** the queued-state bead body named (a) `VersionedSchema` and (b) query+delete as the only two real directions. (c) Reset-Dev-Environment didn't surface because the assumption was "preserve all historical data" — under that constraint, full-wipe-and-reseed loses anything that exists ONLY in cloud (not in local). Once Dustin volunteered that constraint relaxation, (c) became the simplest cleanup move. Lesson: surface the data-preservation constraint as an explicit shape question next time a CloudKit data-integrity bead lands.

- 2026-05-14 — first attempt **FAILED** + reverted same session. Plan claimed schema relaxation (`var completionState: CompletionState = .notDone` → `var completionState: CompletionState? = nil`) was a SwiftData lightweight migration needing no `VersionedSchema`. It wasn't. Build clean, simulator run produced **400+ sync failures per launch** (vs the original ~100 stuck records). The actual error past the `Unknown value class (__NSCFNumber)` flood:
  ```
  invalid attempt to set value type BYTES for field 'CD_completionState'
  for type 'CD_HabitEntry', defined to be: NUMBER_INT64
  ```
  What happened: SwiftData wrapped the new optional `CompletionState?` in a `NSCompositeAttributeDescription` locally (Apple's internal representation for optional `Codable`-enum-as-attribute), while CloudKit's container schema kept `CD_completionState` as `INT64` (the old non-optional shape). Local store wanted to send `BYTES`/dictionary; CloudKit container only accepts `NUMBER_INT64`. Every sync attempt rejected. State was strictly worse than the original problem because the schemas were no longer mutually compatible — not just a few stuck records but ALL writes failing.

  Reverted on 2026-05-14: `Data/Models.swift` field back to non-optional `CompletionState = .notDone`; `effectiveCompletionState` kept as a no-op pass-through (`var effectiveCompletionState: CompletionState { completionState }`) so the 13 read-site renames don't have to revert with the field. Local schema now matches CloudKit again; original ~100-record validation error flood returns, but that's the known floor we started from.

  **Lesson captured to user-level memory:** `~/.claude/projects/-Users-dbpro-Desktop-XCODE-Bullet-Tracker/memory/feedback_ios_real_fix.md` — in iOS on Apple's managed-object stacks (SwiftData / Core Data / CloudKit), apply the canonical Apple-blessed fix; never a shortcut. CloudKit's container schema is a separate registry from the local SQLite store and they must migrate in lockstep. "Lightweight migration" doesn't cover optionality changes when CloudKit is in the picture.

  **Next step (deferred):** the real fix is a `VersionedSchema` + `SchemaMigrationPlan` declaring V1 (non-optional `CompletionState`) → V2 (optional or whatever shape we settle on), plus a CloudKit Dashboard schema deploy to update `CD_completionState`'s server-side type. That's a substantial design surface — re-shape bt-0007 next session before any further attempt. Alternative: attack the problem from the cloud-cleanup side (delete the offending records via CloudKit Dashboard) and leave the schema untouched.
