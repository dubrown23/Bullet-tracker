# Step 0 — prove the dh → Bullet sync with fake data (no dh)

## Why

Dustin wants to log habits by talking to Claude on his iPhone. Voice can only reach a server, so it lands in dustin-health (dh); Bullet Tracker pulls day facts and an inbox of voice actions from dh and grades them itself. The whole design (shared contract in `~/Desktop/Personal/dustin-system/memory/in_flight/habits-voice-dh-bullet-2026-10-26.md`, Part A + Part B) rests on one thing: the app can take facts from outside, grade them, write entries through the normal tap path, and have the result land on iPhone, iPad and the widget **exactly once**. Dustin's ask: prove that first, with fake data, before dh builds anything.

Three facts from the code that make this a real test and not a formality:
- Every tap writes through `HabitStore.setCompletion` (`Habits/HabitDataRepository.swift`), which upserts the day's entry. The fake inbox must use exactly this.
- **Nothing guards against two entries for the same habit and day.** Lookups stop at the first match, so two devices creating the same day's row leave two rows and the UI shows one tick. Invisible today; this bead is the first time it matters.
- No HealthKit anywhere (no entitlement, usage string, or code). Steps are a new permission.

## Design (decided 2026-10-26, Dustin reviewed)

- **Real shape, fake source.** A `HabitFactsSource` protocol answers "today's protein, calories, inbox actions". Step 0 ships one implementation, `FakeHealthFacts`: 190 g protein, 2,050 cal, one inbox action "Test Sauna done". Step 3 swaps in the dh client; grading and writes don't change.
- **Diet grading** is a pure function. Protein ≥ 180 **and** calories 1,900–2,200 → Done; one of the two → Partial; neither → Tried. Targets are constants in Step 0 (Step 2 makes them settings).
- **Sync run** = create Test Diet (multi-state) and Test Sauna (simple) if missing → grade Test Diet from the facts and write it → apply the inbox tick via `setCompletion` → run the cleanup pass → read today's steps. Runs when the app becomes active while the switch is on (`ContentView` already watches `scenePhase`; its `appBecameActive` notification has no listener today), plus a "Run now" button.
- **Cleanup pass (dedupe), deterministic by id.** For each habit + day touched, fetch all rows. If there are two or more, keep the row with the smallest `id.uuidString` and delete the rest. A device that sees only one row deletes nothing, so no sequence of devices can reach zero. Same rule on every device → same winner. No new field; `HabitEntry` has no edit time and Step 0's duplicate rows are identical by construction, so "which wins" carries no information yet. When rows can differ (Step 3, overrides win), the entry needs a source marker anyway; an edit time rides along as the same additive change then.
- **Steps from Apple Health.** `HKStatisticsQuery` cumulative sum of `stepCount` for today, read in the app process. Display only. HealthKit capability is added by Dustin in Signing & Capabilities (project-file action); the usage string goes in `Bullet-Tracker-Info.plist`. Simulator has no step data: device only.
- **Developer section in Settings, `#if DEBUG` only.** Switch "Simulate dh sync", "Run now", steps today, **raw entry count for today per test habit** (the UI alone can't show a double), "Remove test habits".
- **Safety.** Backup first (Settings → Backup & Restore). Only Test Diet / Test Sauna are ever written. Schema untouched: additive code only (the `bt-0007` lesson). Release builds compile none of it.

## Plan

1. `Sync/HabitFactsSource.swift` — `DayFacts` + `InboxAction` value types, `HabitFactsSource` protocol, `FakeHealthFacts` (`#if DEBUG`).
2. `Sync/HabitGrading.swift` — `DietGrade.state(protein:calories:)` → `CompletionState`, targets as constants. Unit-testable, no SwiftData.
3. `Habits/HabitDataRepository.swift` — add `entries(for:on:)` (all rows for a day, no fetch limit), `entryCount(for:on:)`, and `dedupeEntries(for:on:in:)` with the smallest-id rule.
4. `Sync/HabitSyncEngine.swift` — `@MainActor` engine over a `ModelContext`: ensure test habits, grade + write Diet, apply inbox via `setCompletion`, dedupe, publish last-run summary (what was written, counts, steps, errors).
5. `Sync/HealthSteps.swift` — authorization request + today's step count, async/await.
6. `App/DeveloperSyncView.swift` + a `Developer` section in `SettingsView` (`#if DEBUG`).
7. `ContentView` — on `.active`, run the engine if the switch is on.
8. Info.plist usage string; entitlements file gets the HealthKit key when Dustin adds the capability.
9. Build, run on `DBd`, then the pass test below.

## Pass test (Dustin's forced-duplicate version)

1. Backup taken.
2. Switch on from the **iPhone only**. Wait until Test Diet and Test Sauna appear on the iPad before touching it (otherwise each device creates its own pair).
3. Test Diet green, Test Sauna ticked: iPhone ✓ iPad ✓ widget ✓.
4. **Force two rows:** iPad in airplane mode → run the sync on both devices → reconnect the iPad. Pass = the raw entry count for Test Sauna today settles to **one on both devices, never zero**.
5. Steps today matches the Health app.
6. Remove test habits; confirm gone on both devices.

If any step fails: report what failed. dh's Step 1 waits.

## Out of scope

Overrides and "back to auto", Rest grade, targets as settings, re-grading past days, live in-progress colour, pull-to-refresh, any real network call, Lock Screen widgets, the widget's own duplicate of the tick logic (`BulletTrackerWidgetsBundle.swift`).
