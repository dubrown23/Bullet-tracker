# SwiftData migration — Phase 1: swap the engine, model shape unchanged

## Why

`bt-0001` decided it (2026-05-12): migrate the data layer off hand-rolled Core Data onto SwiftData. Phase 1 is the engine swap with the **model shape unchanged** — convert the 6 entities to SwiftData `@Model` types that mirror the current `.xcdatamodeld` field-for-field, so SwiftData coexists with Core Data on the existing App-Group / CloudKit store while consumers migrate area-by-area; the Core Data stack is deleted last. Nothing user-visible ships from Phase 1. The wins land when it's done: flags #1 (three doors), #7 (cache thrash), #8 (calc thread-safety) gone rather than patched; flag #4 (name-keyword workout detection) folded in; a big chunk of hand-rolled plumbing deleted.

Phase 2 (separate later bead) restructures the model — `details` JSON blob → typed, 3-way completion state → one enum, drop vestigial `JournalEntry` fields (blocked on the #9 intent question). Out of scope here.

## Out of scope

- The model *shape* — no entity/attribute restructuring in Phase 1 (that's Phase 2). The `@Model` types mirror the existing `.xcdatamodeld` exactly so coexistence works.
- Repo-layout cleanup (flag #5) — independent, not part of this.
- Any UI / behavior change. Phase 1 is invisible to the user.

## Plan — one focused data-layer push on the `swiftdata-migration` branch

**Strategy (decided 2026-05-12, approach "(b)"):** no Core-Data-coexistence period (the dual-model-sync path was rejected as too fragile for a one-person app). Do the whole data-layer swap in one concentrated effort on a branch; the app won't build/run for the duration; JSON backup (exported from Settings before testing) is the safety net; merge when it compiles + works.

**Data migration:** plan for **in-place open** of the existing `BulletTracker.sqlite` (App Group) with a SwiftData `Schema` that exactly matches what Core Data wrote — that's why `Data/Models.swift` mirrors the `.xcdatamodeld` field-for-field. Fallback if first-launch testing on a *copy* of real data shows problems: migrate to a fresh store (read the old one with a throwaway `NSPersistentContainer` using the kept `.xcdatamodeld`, copy everything into a new SwiftData store, retire the old one) — accepting a one-time CloudKit re-sync.

**CloudKit:** the SwiftData `ModelContainer` is configured `cloudKitDatabase: .private("iCloud.db23.BulletTracker")` on the same App Group store; schemas match → CloudKit record types match → sync continues. Verify on a second device / let it settle.

**Codegen:** `.xcdatamodeld` entities' Codegen → **Manual/None** (then the file is deleted at the end — `NSPersistentCloudKitContainer(name:"Bullet_Tracker")` is gone). The `@Model` classes keep the names `Habit`/`HabitEntry`/etc. (no prefix needed — nothing collides once Core Data is removed).
