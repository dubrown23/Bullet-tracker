# Decide the data foundation: stay on Core Data or migrate to SwiftData

## Why

The entire data layer is hand-rolled Core Data plumbing:
- `CoreDataManager.shared` — `NSPersistentCloudKitContainer`, App Group store, CRUD on Habit/HabitEntry/Collection
- `HabitDataRepository.shared` — `@MainActor @Observable` cache (`habits[]` + `[UUID:[Date:HabitEntry]]`), optimistic UI updates, background-context writes, manual `NSManagedObjectContextDidSave` merge, widget reload
- `HabitCalculationService.shared` — `@unchecked Sendable`, streaks/rates/heatmap, holds its own `viewContext` *and* takes a passed-in context
- Widget extension, `BackupManager`, `JournalPDFGenerator` all touch Core Data directly

This is iOS-only, single-user, CloudKit-synced — squarely SwiftData's design target. A SwiftData rewrite would delete most of `CoreDataManager`, the manual merge dance, the optimistic-update bookkeeping, the save-notification listener, and the `@unchecked Sendable` hack.

But it's a real migration with real risk: the `.xcdatamodeld` becomes `@Model` types (existing-store migration needs care), the widget gets rewritten against `ModelContainer`, the JSON backup format must stay round-trip-compatible, and CloudKit-via-SwiftData has its own constraints. The model is also mid-cleanup (the `JournalEntry` future-log fields, the dual `completed`/`completionState`, the `details` JSON blob) — a migration is the natural moment to fix those, which makes it bigger but more worthwhile.

**This bead is the decision, not the work.** Several patchwork items are downstream and shouldn't be touched until it's settled:
- "three doors into the database" → one owner for Core Data access
- `details` stored as a JSON string blob → typed
- completion state modeled three ways at once (`completed` Bool + `completionState` Int16 + the `useMultipleStates`/`isNegativeHabit` bools) → collapse to the `CompletionStyle` enum
- cache-thrash in `HabitDataRepository` (`clearCache()` on every navigation; the unused `.appBecameActive` notification)
- `HabitCalculationService` thread-safety (`@unchecked Sendable` over a stored context)

If we go SwiftData, those get designed into the rewrite. If we stay on Core Data, they become independent beads in roughly that order (the JSON blob first).

## Plan

**Decided 2026-05-12: migrate the data layer to SwiftData.** Done in two phases. Phase 1 itself builds in stages — SwiftData can coexist with Core Data on the same store, so it gets stood up alongside, consumers migrate area-by-area, the Core Data side is deleted last.

### Phase 1 — swap the engine, model shape UNCHANGED
Convert the 6 entities (`Habit`, `HabitEntry`, `JournalEntry`, `Collection`, `Note`, `Tag`) to SwiftData `@Model` types **field-for-field identical** to the current `.xcdatamodeld`, so SwiftData opens the existing App-Group / CloudKit SQLite store with no data restructuring. Nothing user-visible ships from Phase 1.

- **`Data/`** — delete most of `CoreDataManager` (+`CoreDataManager+HabitDetails`); stand up a `ModelContainer` with the App-Group URL + `cloudKitDatabase: .automatic` (it provides history tracking + remote-change merge for free — the manual `automaticallyMergesChangesFromParent` / merge-policy / history-tracking setup goes away).
- **`App/Bullet_TrackerApp.swift`** — `.modelContainer(…)`; expose the shared container to the widget + backup.
- **`Habits/`** — delete most of `HabitDataRepository` (the cache dict, `loadEntries`/`loadedDateRange`/`clearCache`, batch-load, optimistic-update bookkeeping, the `NSManagedObjectContextDidSave` listener) — `@Query` in views replaces it. Keep `getCompletionState` / `HabitCompletionState`, `reorderHabits`, the post-write `WidgetCenter.reloadTimelines`. Update consumers: `TodayViewModel`, `TodayHabitCardView`, `HabitCompletionDetailView`, `HabitDashboardViewModel`, `HabitDetailDashboardView`, `EditHabitView`, etc. → kills flag #1 (three doors) and flag #7 (cache thrash).
- **`Utilities/HabitCalculations.swift`** — keep the streak / rate / heatmap math; drop the `@unchecked Sendable` + stored-`viewContext` + `using ctx:` plumbing → pure functions over fetched entries, or a `ModelActor` → kills (most of) flag #8.
- **`BulletTrackerWidgets/`** — rewrite `CompleteHabitIntent` + the widget views against a shared `ModelContainer` on the same App-Group store. Highest-risk file alongside the store open.
- **`Journal/` + `Notes/` + `App/SettingsView.swift`** — mechanical `NSFetchRequest` / `CoreDataManager` → `@Query` / `FetchDescriptor` swaps: `DayJournalView`, `JournalExportView`, `JournalJSONExporter`, `JournalPDFGenerator`, `NotesView`, `SettingsView`. No behavior change.
- **`Data/BackupManager.swift`** — keep the `Codable` mirror structs + the backup file format unchanged (old backups still restore); swap the read side to `FetchDescriptor`, the write side to `obj.init()` + `modelContext.insert`. (`BackupRestoreViewModel.swift` is UI state — likely untouched.)
- **Fold in flag #4** — kill the name-keyword "is this a workout?" detection (use `detailType`); that code lives in `HabitDataRepository`, which is getting rewritten anyway.
- **Highest risk:** first launch opening the existing synced store with the new schema. Mitigation: test against a copy of real data before shipping; the JSON backup is the fallback (export before / restore after if it goes sideways). Second: widget + App-Group + SwiftData container agreement.
- **`scope_files` to be locked at activation** after one more close read (the ~18 Core-Data-touching `.swift` files above are the candidate set). Phase 1 may be split into its own build bead at activation with this bead as the decision record — decide then.

### Phase 2 — clean the model (separate bead; only after Phase 1 ships and is stable)
- `details` JSON-string blob → typed fields / child `@Model`s (workout types/duration/intensity, reading book/pages, mood). SwiftData `SchemaMigrationPlan` + one-time backfill parsing the old JSON. *(flag #2)*
- Collapse the 3-way completion state (`completed` Bool + `completionState` Int16 + the `useMultipleStates`/`isNegativeHabit`/`trackDetails`/`detailType` bools) → one canonical value (an enum, stored directly). Map old data. *(flag #3)*
- Remove the vestigial `JournalEntry` future-log fields (`isFutureEntry`, `isSpecialEntry`, `hasMigrated`, `targetMonth`, `scheduledDate`, `specialEntryType`, `taskStatus`) — **blocked on the open #9 question**: what was the "future log / migration" feature meant to do? Dead → remove; want-it-someday → park.
- Plan stays at this level until Phase 2's own design pass (after Phase 1).

### Still independent of this chain (anytime)
- Flag #5 — repo-layout cleanup / stray-file deletion (`WidgetEnums.txt`, committed `.DS_Store`s) / archive old `Documentation/`.
