# Burned before Oct 27 on rest days — the Dashboard's burned trend leans high

Follow-up from `bt-0023`'s cleanup pass (2026-10-29). Small.

## Why

`bt-0023` stores the day's calories burned (Apple Health active + resting)
on the **Workout row**, and the one-time Refresh Workout Calories pass
wrote it onto the rows that exist. Before the Oct 27 go-live a Workout row
exists only on days dh has a session (`bt-0022` rebuilt them that way), so
for Aug 1 → Oct 26 burned is known on training days and missing on rest
days — missing, not zero. Any Dashboard average or trend of burned that
reaches back into that span leans high. From Oct 27 on the sync writes a
Workout row's block every day it grades, so the gap is only historical.

## Options (pick at design pass)

1. **Backfill from Health.** A second one-time pass (or a row in the same
   Refresh screen) reads active + resting for every day Aug 1 → Oct 26
   with no Workout row and stores it. Needs somewhere to put a burn on a
   day with no row: either a `notDone` auto Workout row carrying only
   `health` (the grader already tolerates details-only rows), or a new
   per-day place outside habit rows.
2. **Start burned trends at Oct 27.** `DashboardTrends.trainingSeries`
   clamps the Burned series to the Diet / Workout go-live; Month view over
   the old span says "Burned from Oct 27".

Option 2 is the honest one-liner; option 1 is the complete one. Decide
with Dustin.

**Decided 2026-10-30 (Dustin): option 1, backfill from Apple Health.**
One time, Aug 1 → Oct 26, the same active + resting total the sync reads
(`HealthSteps.burn`). Days from Oct 27 on are never read or written; no
grade changes. Scope grew by `App/SettingsView.swift` (the new one-time
row) and `Habits/HabitDataRepository.swift` (a write that can create a
row), both confirmed at activation. His addition: days in the span that
HAVE a Workout row but no burn get their burn filled too — Health block
only, grade / source / note / sessions untouched — and the screen says
how many there are, or that there are none.

## Plan

1. `Sync/HealthRefetch.swift` — `BurnBackfill`, pure over a `ModelContext`
   like the refresh beside it: fixed span Aug 1 → Oct 26; `load` reads
   Health burn for the days that need one (rowless days + rows without a
   burn); `plan` splits the span into days with a burn already, rows
   missing a burn, rowless days, days Health had nothing for, and the
   Burned average before / after (mean of `totalBurnKcal` over days with a
   reading); `perform` writes the adds and stamps `burnBackfillDoneAt`.
2. `Habits/HabitDataRepository.swift` — `HabitStore.setHealthCreatingRow`:
   like `setHealth`, but when the day has no row it creates one with
   `.notDone`, `source = .auto`, no details, only the `health` block. Such a
   row is invisible to the win rule, the Journal (notDone + no details),
   streaks and rates, the Today dot, and the sync (before go-live).
3. `App/HealthRefetchView.swift` — `BurnBackfillView`: iPhone + Health
   only; counts first (days in span, days with a burn, rows missing a burn
   or "none", rest days to add, days Health had nothing for, average
   before → after), one Backfill button, a Done section with the same
   numbers. `App/SettingsView.swift` — "Backfill Burned Calories" row under
   Data Management, hidden once run (`@AppStorage` on the done key).
4. Tests — the plan picks rowless days and rows without a burn, skips
   days with a burn and anything after the span, computes both averages;
   perform creates an empty automatic row with only a Health block and
   fills an existing row's burn without touching state / source / sessions;
   the created row is not logged, not an override, and has no details.
5. Dashboard — no change: `trainingSeries` already reads any row's burn.

## Build notes (2026-10-30)

Built in plan order. `BurnBackfill` sits under `HealthRefetch` in the same
file; `BurnBackfillView` under `HealthRefetchView`. `HabitStore.setHealthCreatingRow`
is the one new write; it skips `didWrite` (nothing to sync, nothing on the
widget — the day is before go-live). The plan reads Health only for the days
that need it (`daysNeedingBurn`), never for days whose row already has a
burn. Two tests: the fixed span (87 days) and a four-day fixture — a row with
a burn untouched, a hand-graded row gaining only its burn, a rowless rest day
gaining an empty automatic row, a day Health had nothing for counted but not
written, averages 3,000 → 2,700, and the Dashboard's Burned series reading
the rest day. 110 tests on the Duo simulator.

## Pass (2026-10-30 afternoon, DBd)

Counts on the screen: 87 days in span, 70 with a burn already, rows
missing a burn: None, 17 rest days with no row, burn added on 17 days,
**Burned average 3,354 → 3,228.2** (the 17 rest days average ≈ 2,710).
Backfill tapped, Done section matched. Dashboard Month view: the Burned
row has a bar for every day of October, no gaps before Oct 27, avg 3,144.
Found on the way: the day view's Calories block (Eaten vs Burned) is hidden

day's Burned never shows there — pre-existing from `bt-0023`, logged as an
open thread for Dustin's call. **Shipped.**
