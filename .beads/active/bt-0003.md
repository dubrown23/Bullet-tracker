# SwiftData Phase 2 — model restructure + drop dormant journal machinery

## Why

`bt-0001` decided the SwiftData migration is two-phase. `bt-0002` shipped Phase 1 — engine swap, model shape unchanged. This bead is Phase 2: clean up the model itself.

Five things land here:

1. **Drop the dormant journal machinery.** The original app vision included a "full digital bullet journal" layer — collections, tags, scheduled future entries, task migration, drafts. The model was scaffolded but the UI was never wired. Today's Journal tab uses `Note` (date + content + id) and reads `HabitEntry`. `JournalEntry`, `Collection`, and `Tag` are completely dormant — only the JSON backup path touches them, faithfully round-tripping records that nothing creates. **Decision 2026-05-13 (resolves STATUS Open Question #9):** drop these three `@Model` types and their backup mirror structs entirely. No migration of historic records — the bullet-journal system didn't fit Dustin's actual use, and the live Journal tab keeps working untouched (it's on `Note`). This also folds in the seven vestigial future-log fields the patchwork-flags-review surfaced (`isFutureEntry`, `isSpecialEntry`, `hasMigrated`, `targetMonth`, `scheduledDate`, `specialEntryType`, `taskStatus`) — they go with `JournalEntry`.

2. **Lift `HabitEntry.date: Date? → Date`.** Currently optional from the original Core Data schema. `bt-0004` proved that SwiftData's `#Predicate` rejects every shape of optional-`Date` comparison on this iOS version, which forced the perf-pass predicate rewrite to defer. Making this field non-optional is the right structural fix — and the natural home is a `VersionedSchema` migration here in Phase 2.

3. **Collapse the 3-way completion state.** Today `HabitEntry` carries both `completed: Bool` (vestigial, marked vestigial in code but still written) AND `completionState: Int16` (the real state, with magic numbers 0/1/2/3), and overlapping habit-level flags (`useMultipleStates`, `isNegativeHabit`, `trackDetails`, `detailType`) duplicate intent. The `CompletionStyle` enum already exists as the intended model. Collapse to that enum + one state value; drop `completed`.

4. **Type the `details` JSON blob.** `HabitEntry.details: String` holds `JSONSerialization` dicts for workout types/duration/intensity, book/pages, mood — every screen hand-parses by string key (`json["types"]`, `json["duration"]`, etc.). Replace with a typed `Codable` struct (or child entities if a relational shape fits better — design-pass call).

5. **Rewrite the deferred `bt-0004` hot-path predicates.** Three `HabitStore` reads (`entry(for:on:)`, `entriesByDay`, `allEntriesByDay`) + two widget per-habit sites currently fetch all entries and filter in Swift. With `date` non-optional after item 2, the `#Predicate` rewrite is mechanical — ~50 lines. The `#Index` on `HabitEntry.date` is already in place from `bt-0004`.

This is a **SwiftData `VersionedSchema` migration** against the live CloudKit-synced store — real care needed on schema versioning, backup-format change, and CloudKit-with-SwiftData constraints during the lift.

## Out of scope

- The `ModelActor` for dashboard aggregation (`bt-0002` watch-item d / `bt-0004` non-shipped option). That's its own perf decision; not bundled here.
- Cross-device CloudKit sync verification (STATUS Next #2) — independent device-test, not gated on Phase 2.
- Repo-layout cleanup (STATUS Next #3) — independent hygiene work, not gated on Phase 2.
- The half-built "create collection" surface in `SettingsView` gets removed as part of item 1 (dropping `Collection`), but no new UI work is in scope here.

## Decision log

### Call A — `details` blob typing → **typed shape on the entry**

Decision (2026-05-13): `HabitEntry.details` becomes a typed `HabitEntryDetails` Codable enum (a discriminated union by `DetailKind`), persisted by SwiftData as an attribute. Reads stop hand-parsing JSON strings; UI sites switch to typed access.

Why this over the alternatives:
- (b) child `@Model` entities per detail kind = pure ceremony; the payload is leaf data, never queried, never joined. Extra deletion-rule wiring, extra backup-format work, no real win.
- (c) flat columns per possible field on `HabitEntry` = most rows nil-bloated; loses the discriminated structure.

Migration vehicle: **Path 1 (SwiftData one-shot transform) first, Path 3 (wipe + restore via existing `BackupManager` pipeline) as fallback.** Path 2 (dual-field bridge) explicitly rejected — months of dual-shape code, two follow-on beads, worst-case complexity. Path 4 (plain wipe, no restore) rejected — historical habit data isn't vital but isn't garbage; the patterns-over-time view is the app's substrate.

Honest read flagged during shape: bt-0004 already proved SwiftData on this iOS version rejects shapes that "should" work (optional-Date predicates). Same risk class here for the `String → HabitEntryDetails` attribute-type transform. If Path 1 rejects, Path 3 is pre-designed as the fallback; no design re-open at 11 pm during build.

### Call B — Habit-level flag collapse → **full collapse (c)**

Decision (2026-05-13): drop all 4 legacy `Habit` flags. Replace with two enums.
- `Habit.completionStyle: CompletionStyle` (the enum already exists in `HabitFormView.swift`, moves to `Data/Models.swift`): `.simple / .multiState / .avoidance`.
- `Habit.detailKind: DetailKind?` (new): `nil / .notes / .workout / .reading / .mood`. `nil` = no detail capture.

Why over (a) entry-side only or (b) half-collapse:
- The duplicate-intent pattern is **already documented in the code as conversion gymnastics** — `CompletionStyle.from(useMultipleStates:isNegativeHabit:)` and `.asBools` exist as the workaround. Collapsing storage *deletes* that code instead of adding any.
- The UI layer already speaks `CompletionStyle`. `HabitFormView` has `@Binding var completionStyle: CompletionStyle`. Bools-to-enum conversion happens at the storage boundary today; collapsing means storage and UI finally agree.
- Pairs cleanly with Call A: `HabitEntryDetails` is naturally discriminated by `DetailKind`. If `Habit.detailKind` is the same enum, the entry's payload type is determined by the habit's setting — self-documenting. A string `detailType` would make that pairing asymmetric.
- Marginal cost (c) over (b) is small — every consumer file is already in scope from (b).

### Call C — bead scope → **all 5 items in bt-0003 (a)**

Decision (2026-05-13): keep all 5 items in bt-0003. Build executes in 6 internal waves (above). Ships as one bead, one migration event.

Why over (b) 2-bead split or (c) 3-bead split:
- One migration vehicle (Path 1 or Path 3) is the same event whether we change 1 thing or 5. Splitting multiplies migration events without reducing per-event complexity.
- Items cluster tightly: 3+4 share the new `DetailKind` enum; 2+5 share the non-optional date field; 1 is almost entirely in `BackupManager`. Splitting forces file overlap across `scope_files`, which the phase-gate hook will fight.
- bt-0002 already proved the bead system handles bigness via internal waves (~3500 lines, 6 waves, shipped clean).
- bt-0001 conceived Phase 2 as a single "model restructure" bead. Splitting now is scope drift after the design pass, not improvement.

The (b) seam "model shape vs perf work" sounded clean during shape but item 2 (non-optional date lift) IS a schema migration — has to ride the same event as items 1/3/4. Splitting it reintroduces the dual-migration cost it was trying to avoid.

### Wave 0 — Pre-flight enable (backup-restore `@MainActor` fix)

Decision (2026-05-13): backup-restore round-trip crashed at pre-flight (Dustin-side test, Settings → Backup & Restore → Create Backup File). Device debugger showed `EXC_BREAKPOINT` at `BackupRestoreViewModel.handleBackupSuccess` line 228, `viewController.present(activityVC, animated: true)` — `_dispatch_assert_queue_fail` because the call ran off the main thread.

Root cause: `bt-0002` migrated the backup code to async `Task`s when it swapped the data engine, but did not annotate `BackupRestoreViewModel` as `@MainActor`. Unstructured `Task { }` does NOT inherit actor isolation from a non-isolated class, so the post-await success handler ran on a background thread. UIKit's `present(_:animated:)` requires main → crash. (This is `bt-0002`'s "backup round-trip device-test deferred, low-risk" watch-item flipping from low-risk to active.)

Fix: added `@MainActor` to both `BackupRestoreViewModel` (Observable class, drives SwiftUI) and `BackupPickerDelegate` (pairs naturally — `UIDocumentPickerDelegate` callbacks fire on main per UIKit contract). With the class on `@MainActor`, the enclosing `Task { }`s now inherit main-actor isolation; the existing `await Task.detached { ... }.value` still hops off main for the heavy backup/restore work and resumes back on main.

Adding `@MainActor` surfaced three Swift 6 strict-concurrency follow-ons (same session, same Wave, all mechanical):
- **`deinit` is nonisolated even on `@MainActor` types.** Fixed by marking the two observer storage properties `nonisolated(unsafe)` — they're set only on `@MainActor` paths and `NotificationCenter.removeObserver(_:)` is thread-safe per Apple docs; `unsafe` accurately describes "safe, the compiler just can't prove it."
- **`NotificationCenter` block observers with `queue: .main` run on the main *thread* but not in the main actor's *execution context*** (Swift 6 distinction). Fixed by wrapping the two progress-property writes in `Task { @MainActor in self?.backupProgress = progress }` so the actor hop is explicit.
- **Original popoverPresentationController Main Thread Checker hit at (pre-edit) line 219** was from the run BEFORE the `@MainActor` annotation landed — stale console output, not a separate issue.

`Data/BackupRestoreViewModel.swift` final line count: 477 → 508 (+31, all additions — 2 `@MainActor` annotations + 2 `nonisolated(unsafe)` + 2 `Task { @MainActor in }` wrappers, each with a doc-comment explaining WHY so the rules aren't accidentally peeled off later).

Why this stays inline as Wave 0 of bt-0003 and not a separate bead:
- ~3-line mechanical `@MainActor` fix; `feedback_when_to_bead`'s "default to inline" applies (no real `## Plan` tradeoff — there's one right answer).
- `Data/BackupRestoreViewModel.swift` is already in bt-0003's `scope_files` (Wave 4 + Wave 6 touch the backup pipeline anyway).
- bt-0003 Plan said "stop and fix backup-restore before any wave touches the model"; fixing as Wave 0 of bt-0003 IS that. Separate bead would be process-overhead.

Gate: Wave 1 starts only after Dustin reproduces the pre-flight backup-restore round-trip successfully (export → save off-device → import → state matches before/after). **Pre-flight passed 2026-05-13.**

### Wave 1 — Drop dormant machinery

Decision (2026-05-13): deleted `Collection`, `JournalEntry`, `Tag` `@Model` types (and the 7 vestigial "future log / migration" fields that lived inside `JournalEntry`) entirely from the live SwiftData schema, plus all their backup-mirror plumbing.

Files touched + line-count deltas:
- `Data/Models.swift` 242 → 134 (−108): dropped 3 `@Model` classes + `Habit.collection` relationship + corresponding init param; updated file header to reflect Phase 2 progress.
- `Data/DataStore.swift` 60 → 58 (−2): dropped 3 types from `Schema([...])`.
- `Data/BackupManager.swift` 515 → 386 (−129): dropped 3 fetcher methods + 3 import methods + 3 mirror structs (`CollectionData`/`JournalEntryData`/`TagData`) + `HabitData.collectionID` + corresponding `BackupData` fields + dormant-type deletions in `clearExistingData`.
- `App/SettingsView.swift` 369 → 349 (−20): dropped `defaultCollectionNames` constant + `createDefaultCollections` method + the dormant deletes in `clearAllData`.

**Backup-format compatibility preserved.** `BackupData` lost three top-level fields (`collections`, `journalEntries`, `tags`) and `HabitData` lost `collectionID`. Old backup files that carry those keys still decode cleanly — `JSONDecoder` ignores unknown keys by default, so the dormant data is silently dropped on restore. New backups simply don't emit them.

Smoke build: clean (`** BUILD SUCCEEDED **`, `xcodebuild -scheme "Bullet Tracker" -configuration Debug -destination "generic/platform=iOS"`).

**Wave 0 follow-on (same wave, surfaced by Wave 1's smoke build):** the cosmetic `nonisolated(unsafe) has no effect` warning Wave 0 left behind led to two failed attempts to "fix" it (bare `nonisolated`, then `@ObservationIgnored + nonisolated`). Both failed to compile — the compiler rejects bare `nonisolated` on mutable stored properties ("convert to `let` or use `nonisolated(unsafe)`"), so the warning's own suggestion was misleading in the context of `@Observable`. Final correct form: `@ObservationIgnored private nonisolated(unsafe) var <observer>: NSObjectProtocol?` with a doc-comment recording the dance so future-Dustin doesn't repeat the warning-chase. Warning suppressed; the `@ObservationIgnored` is also semantically correct (these references aren't UI state).

### Wave 1 → Recovery / Plan pivot

Decision (2026-05-13): Wave 1 shipped to device and hit the migration risk the original Plan named but mis-scheduled. CloudKit's routine `HistoryExpired` event (7-day transaction-history reset) coincided with the local schema-vs-store mismatch; SwiftData's default reconciliation produced invalidated `HabitEntry` model instances. `HabitEntry.date.getter` then fataled on any access to a no-longer-snapshotted record (`HabitEntry/p1600` in the crash log).

**Root mistake in the original Plan:** the migration vehicle was scheduled at Wave 6. For a bead that changes schema starting at Wave 1, the migration vehicle is required Wave-1 infrastructure, not Wave-6 polish. The wave plan was pattern-matched from bt-0002 (which only swapped the data engine, didn't change schema shape) — wrong predecessor.

**Recovery executed:** disabled CloudKit at the code level (`Data/DataStore.swift`: `cloudKitDatabase: .automatic` → `.none`). Dustin deleted the app on the iPhone, reinstalled fresh from the `swiftdata-phase2` branch, restored from the pre-flight JSON backup. All habits, entries, and notes returned cleanly. **Path 3 (wipe + restore via the existing `BackupManager`) is now proven end-to-end as the migration vehicle for this bead.**

**Plan pivot consequences (Plan section above reflects this):**
1. **Path 1 dropped entirely from scope.** No `VersionedSchema`, no `SchemaMigrationPlan`. Path 3 is the only migration vehicle. bt-0004 already showed SwiftData on this iOS version is finicky; Path 3 just proved itself first try; the case for spending more code on Path 1 evaporated.
2. **6 waves collapsed to 5.** Original Waves 2 / 3 / 4 (date-lift, flag-collapse, details-typing) merged into a single Wave 2 — all schema changes ship in one event.
3. **CloudKit stays OFF for the duration of the build.** Re-enabled only at Wave 5 (ship). During build, Dustin uses the app in single-device mode — no cross-device sync. Acceptable for the bead's duration; widget keeps working since it shares the App-Group store.
4. **Consumer rewrites consolidated into Wave 3.** Touches every file that read the dropped fields. Project does not compile between Wave 2 (schema landing) and Wave 3 (consumers catching up); smoke build runs only at end of Wave 3.
5. **Wave 4 (hot-path predicates) unchanged in content, renumbered.**
6. **Wave 5 (ship) absorbs the migration-vehicle work that was originally Wave 6** — the actual user-facing migration moment is one explicit ceremony at ship time, not woven through every wave.

Branch: `swiftdata-phase2`. Wave 2 next: combined schema changes.
