# Send hand taps to dh automatically — so "what's left today" by voice knows what I tapped

Planned 2026-10-28 evening from the code, for Dustin's go in the morning. **No code until go.** His four questions are answered under his own numbers (1, 2, 5, 6); the widget and two edge cases follow. Plan reviewed by Dustin the same evening: good, widget answer agreed, one gap added — **leaving the app right after a tap** (section 7, placed before the tests it adds to).

## Why

Step 3 (`bt-0019`, shipped 2026-10-27) sends today's hand ticks to dustin-health as part of every sync, so Claude voice's "what's left today" can skip what Dustin already tapped. But a sync only runs when the app opens or when he pulls down on Today. In the pass test he tapped Pills, asked "what's left today", and Pills was still listed — the tap hadn't travelled yet. He had to pull down first.

Wanted (Dustin, 2026-10-27): after any hand tap — on Today, in Log Details, or on the widget — the iPhone sends a **quiet sync a few seconds later**, and several taps in a row make **one** sync, not one each. iPhone only, same rule as grading and the rest of the sync; the iPad never calls dh.

## What's true in the code tonight (checked 2026-10-28)

- Every hand write in the app ends in one of three functions in `Habits/HabitDataRepository.swift`: `HabitStore.setCompletion` (line 170), `HabitStore.removeEntry` (192) and `HabitStore.updateEntryDetails` (201). Today's squares and Rest (`TodayHabitCardView.swift:408–439`), Log Details' Done and Clear Entry (`HabitCompletionDetailView.swift:521, 554`) and Back to Auto (`HabitSyncEngine.revertToAutomatic`, which removes the row then runs a forced sync) all go through them. There is no fourth path.
- All three already end the same way: save, then `reloadWidgetIfToday` (line 363) — "if this was today, redraw the widget". That is the exact condition dh cares about too: `op=sync` only carries **today's** ticks (`payload`, engine line 454), so a tap on a past day has nothing to send.
- The engine's own writes use the same functions with `source: .auto` (grader, lines 588–600) or `.voice` (inbox, 637–662). `removeEntry` has no `source` argument yet, so tonight a grader "drop back" and a hand clear look the same to the store.
- dh **replaces** its ticked list on every sync (`supabase/migrations/0011_habit_inbox.sql:611`, `app_ticked_habits = array(...)`), so an un-tick travels exactly like a tick: the next list simply doesn't have it.
- The engine throttles an on-open sync to one per 120 s (`minimumInterval`); pull-down and Save always run. `run` refuses to start while one is running (`guard !isRunning`), and it builds the tick list at the top, before any network call.
- The widget writes from its own process with its own `ModelContext` (`BulletTrackerWidgetsBundle.swift:96–149`). It has no `HabitStore` (app target only), no `DustinHealthSource` (app target only) and no key (the Keychain item has no shared access group). It already stamps `lastWidgetUpdate` into the App Group defaults after every tap (line 147).
- Nothing on Today shows a sync in progress; only Settings → Dustin's Health and the Developer screen read `isRunning`. A sync is already "quiet" from the Today tab.
- `ContentView` already watches `scenePhase` and runs the on-open sync on `.active` (line 54–61). Nothing watches `.background`. Locking the phone goes `.active` → `.inactive` → `.background` within about a second, and iOS then suspends the app: a plain `Task.sleep` timer stops with it and only resumes on the next open. Apple's short finish-up window is `UIApplication.beginBackgroundTask(withName:expirationHandler:)` (checked in the docs 2026-10-28); it gives roughly 30 s, must be balanced by `endBackgroundTask`, and Apple says to request it **before** the app enters the background, not on the way out, or it may not be granted in time.

## Plan

### 1. Where the trigger goes — one place

The hook lives where the widget redraw already lives: the end of the three store writes. `reloadWidgetIfToday(dayStart)` becomes `didWrite(dayStart, source:)`, which does what it does today and, **when the day is today and the source is `.hand`**, tells the engine "a tap landed". No screen is touched: Today, Log Details, Back to Auto and any future screen get it by calling the store, same as now.

```
before                                   after

Today square ─┐                          Today square ─┐
Log Details ──┼→ HabitStore.write ─→ save ─→ redraw widget
Back to Auto ─┘                          Back to Auto ─┘        └→ (today + hand) → engine.noteTap()
                                                                                        │
                                                                                   wait 3 s, one sync
```

Two small changes make the condition honest:

- `removeEntry` gains `source: EntrySource = .hand`, like the other two. The engine passes `.auto` for a drop-back (line 588) and `.voice` for a voice un-tick (644, 652); the three hand callers change nothing. So grader and voice writes, which happen **inside** a sync, never schedule another one (no sync → voice tick → sync loop; the voice action is already acked).
- A tap on a past day (Journal, or a left-hand square on Today) schedules nothing — there is nothing in `op=sync` for it.

The call from the store to the engine is one line (`Task { @MainActor in HabitSyncEngine.shared.noteTap(in: context) }`); the store already talks to WidgetCenter from the same spot, so this is the same kind of after-write side effect, not new coupling.

### 2. Several taps make one send — a 3-second wait, restarted by every tap

```
tap   tap   tap                       one sync
 │     │     │                           │
 ▼     ▼     ▼                           ▼
 ├─ 3 s ─┤                                            (each tap throws away the old timer)
       ├─ 3 s ─┤
             ├────── 3 s ──────┤→ run: op=sync first (dh knows ~1 s later), then changes / inbox / facts / grade as usual
```

- **Why 3 seconds.** Cycling a multi-state square (Done → Partial → Tried → clear) is about a tap a second, so 1 s would split one cycle into two or three sends. Lifting the phone and saying "what's left today" takes longer than 4 s, so dh knows (3 s wait + ~1 s for the first request) before Claude asks. 10 s would lose the race he actually ran in the `bt-0019` pass test. A constant (`quietSyncDelay`), so changing it is one number.
- **What the sync is.** The same full run as pull-down (`refresh(force: true)`): one code path, nothing new on the wire (`op=sync` already carries the ticks, and it's the **first** call of the run, so the tick lands at dh within about a second of the timer firing). Cost per burst: the usual four or five requests, same as one pull-down. A "ticks-only" run would save three requests and add a second path to keep right; not worth it.
- **A sync that starts for any other reason drops the waiting one.** Open, pull-down, Save, Back to Auto: `run` cancels the pending timer as its first act. Safe because `run` builds the tick list at the top, after the tap's save, so that sync already carries the tap. This is also what keeps Back to Auto at **one** run (its own forced run, not a second one 3 s later).
- **A tap during a running sync is not lost.** That sync's list was built before the tap. The timer fires at 3 s; if a run is still going it waits (half-second checks) and goes when the run ends. The waiting task is the only thing ever cancelled; a running one is never interrupted (a cancelled task would abort its own network call mid-flight).
- **Leaving the app inside the 3 s does not lose the tap either** — section 7.

### 5. iPhone only

`noteTap` schedules a timer only when `isConnectedToHealth` is true: `isGradingDevice` (user-interface idiom is phone — the Duo is a phone) **and** a key is in the Keychain. On the iPad, or an iPhone with no key, nothing is scheduled: no timer, no network, exactly as now. One exception for testing: in debug builds with the Developer fake switch on, the quiet sync runs the fake (same choice `refresh` already makes), so the 5-taps test can be watched on the simulator.

This is a pure decision function (`shouldQuietSync(isPhone:hasKey:source:isToday:)`) so the table is unit-tested without faking a device.

### 7. Leaving the app with a tap still waiting (Dustin's gap, 2026-10-28)

The hole: tap Pills, lock the phone within 3 s. iOS suspends the app, the timer never fires. On the next open the 120 s throttle can skip the on-open sync, so Pills never reaches dh until a pull-down — the exact bug this bead fixes. Two layers close it: send at once on the way out, and never let the throttle hide a waiting tap.

```
tap Pills ──┬─ timer armed (3 s)
            ├─ "tap waiting since 9:41:02" written to disk
            └─ background window taken now (Apple: take it before leaving, not on the way out)
                     │
     lock the phone ─┤  scenePhase → .background
                     ▼
            timer dropped, the sync runs NOW inside the window (op=sync first → dh knows in ~1 s)
                     │
                     ├─ sent OK   → "last sent" = run start; window released; app suspends as usual
                     └─ not sent (no network, window expired, app killed) → "tap waiting" stays newer than "last sent"
                                                                              → the NEXT OPEN syncs regardless of the throttle
```

**Layer 1 — send on the way out.** When a tap arms the timer, the engine also takes a background task assertion (`beginBackgroundTask(withName: "Send taps to dh")`), so the window is already held if he locks the phone a second later. `ContentView`'s existing `scenePhase` watcher gets a `.background` branch next to the `.active` one: it calls `HabitSyncEngine.shared.appLeftForeground()`, which, **only if a tap is waiting**, drops the timer and starts the same run at once. The assertion is released when the run ends, when the timer is cancelled by another run, or by the expiration handler if iOS runs out of patience. With nothing waiting, leaving the app does nothing new. A full run is a few seconds, well inside the window; if it ever proves slow in the background, the fallback is to narrow the background path to `op=sync` alone — not built unless needed.

**Layer 2 — the backstop, same shape as the widget stamp.** The engine keeps two dates on disk (standard defaults): `tapWaitingSince`, written synchronously at every hand tap on today before the timer is even armed; and `lastSentAt`, written only after an `op=sync` **succeeds**, holding that run's **start** time (not its end — a tap that lands mid-run is newer than the start and so still counts as waiting). On `.active`, `refresh` runs regardless of the 120 s throttle when either `tapWaitingSince` or the widget's `lastWidgetUpdate` (App Group defaults) is newer than `lastSentAt`. No explicit clearing step: a date comparison can't be left in the wrong state by a crash, a kill, a failed request or an expired window. This replaces the "compare the widget stamp with the last attempt" wording in the widget section below — both stamps now mean the same thing and go through the same check.

**Unit tests (Swift Testing, in-memory store with `cloudKitDatabase: .none`, in `SyncEngineStep3Tests`).** The engine gets a test seam: a counting fake source (`sync()` increments a counter and records the last payload) plugged in for the quiet sync, and the delay shortened to 0.2 s.

1. `fiveQuickTapsMakeOneSend` — five `HabitStore.setCompletion` calls on today, wait one second → one `sync()` call, and its `tickedToday` reflects the final state.
2. `autoVoiceAndPastDayWritesSendNothing` — an `.auto` write, a `.voice` write, an `.auto` remove, and a hand tap on yesterday → zero calls.
3. `aStartingRunDropsTheWaitingOne` — a hand tap, then a forced `refresh` at once → one call total, and its payload already carries the tap.
4. `quietSyncDecisionTable` — the pure function: phone + key + hand + today → yes; iPad → no; no key → no; `.auto` / `.voice` → no; yesterday → no.
5. `leavingTheAppSendsTheWaitingTapNow` — a hand tap, then `appLeftForeground()` straight away → one call with no wait, and no second call after the delay would have elapsed. With nothing waiting, `appLeftForeground()` makes no call.
6. `aWaitingTapBeatsTheThrottle` — the pure on-open decision (`shouldRunOnOpen(lastAttempt:now:tapWaitingSince:widgetStamp:lastSentAt:)`): inside the 120 s window with every stamp older than `lastSentAt` → skip; a tap stamp newer → run; a widget stamp newer → run; a tap that landed after a run **started** but before it finished → still newer than `lastSentAt`, so run.

### The widget (not in Dustin's list; my recommendation)

A widget tap **cannot** send on its own: the widget process has no key (the Keychain item isn't shared) and no sync code (`DustinHealthSource` and `HabitStore` are app-target only). Giving it both means a shared Keychain access group entitlement, a second network client, and adding files to the widget target — a `project.pbxproj` change the hook blocks, so Dustin would do it by hand in Xcode. Not worth it for this bead.

What this bead does instead, so the lag is one app open and never longer: the widget's existing `lastWidgetUpdate` stamp (App Group defaults) is the second input to the section 7 backstop — when the app becomes active and the widget wrote since the last successful send, the on-open sync runs **regardless of the 120 s throttle**. Today a widget tap followed by an open inside two minutes of the last sync waits for the throttle; after this it doesn't. The widget file itself does not change. Dustin agreed 2026-10-28. If the widget lag still annoys him, it is its own bead (and it would be the same shape as the parked silent push: work the app can't do from the foreground).
