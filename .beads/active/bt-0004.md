# SwiftData data-layer perf pass — targeted predicates + dashboard calc actor

## Why

`bt-0002` Phase 1 swapped the data engine but left two known perf shortcuts in place — explicitly deferred to ship Phase 1 sooner. Both are observable in the bt-0002 Decision log as watch-items (d) and (e):

- **(d) Dashboard aggregation runs on `@MainActor`.** Wave 2 dropped the old background-Core-Data-context dance — the dashboard now does its aggregation on the main thread. Fine at current data sizes; can hitch a frame or two on the year view after years of dense data. The shape that would fix this is a SwiftData `ModelActor` (~same role as the old background context, ~30 lines).

- **(e) `HabitStore` reads filter `habit.entries` in memory.** Every fetch in the SwiftData migration is `(try? context.fetch(FetchDescriptor<X>())) ?? []` followed by an in-Swift filter. `HabitStore.entry(for:on:)`, `HabitStore.entriesByDay`, `HabitStore.allEntriesByDay`, `DayJournalViewModel.loadHabitEntries`, the widget's `fetchTodaysHabits` — all of them. For a habit tracked daily for years that means hundreds-to-thousands of objects faulted per habit per Today-list render. The shape that would fix this is `FetchDescriptor<HabitEntry>` + `#Predicate` on `habit.id` + date range, with a fetch limit. Wave 2 dodged it because `#Predicate` over optional relationships was fiddly mid-migration; standalone work it's doable.

This is **perf work, no behavior change.** The model shape stays exactly as Phase 1 left it — that's why this is its own bead and not folded into `bt-0003` Phase 2 (where the model shape *does* change, and which is blocked on the #9 Journal-intent question). Decoupling lets perf ship whenever convenient instead of waiting on #9.

There's also an indexing piece worth flagging now (not committing to scope yet): the original `.xcdatamodeld` had fetch indexes on `HabitEntry.date` and `JournalEntry.date` (named `byDateIndex`). `Models.swift` doesn't recreate them — `#Index<HabitEntry>([\.date])` would. Whether to add at design pass.

## Out of scope

- **Model shape changes — including lifting legacy-optional fields.** No typing the `details` JSON blob, no collapsing the 3-way completion state, no dropping vestigial `JournalEntry` fields — that's `bt-0003` Phase 2. Lifting `HabitEntry.date: Date? → Date` (and any other legacy-optional fields the original `.xcdatamodeld`-mirror left in `Models.swift`) is *also* `bt-0003`'s territory, even though it'd unblock this bead's item 1 — those are model-correctness fixes, not perf, and they need a proper SwiftData `VersionedSchema` + `SchemaMigrationPlan` for the live CloudKit-synced store.
- **Behavior changes.** No new features, no UX changes. Perf only.
- **Backup file format.** The `Codable` mirror structs in `BackupManager` stay byte-identical.
- **Widget redesign.** Just the data-path inside the widget's existing timeline provider + intent, not the widget's UI shape.

## Plan

Four targeted changes. Perf only — no behavior changes, no model-shape changes.

1. **Hot-path predicate fix — DEFERRED to `bt-0003`.** Discovered at build time that SwiftData's `#Predicate` on this iOS version rejects every shape of optional-`Date` comparison we tried (`entry.date!` force-unwrap, `(entry.date ?? Date.distantPast)` nil-coalesce inline, captured-local sentinel) — none reduce to `StandardPredicateExpression<Bool>` when combined with a relationship-equality clause. The clean fix is `HabitEntry.date: Date? → Date`, which is a SwiftData schema-migration (not lightweight), interacts with the live CloudKit-synced store, and belongs in the model-restructure surface `bt-0003` already owns. See Decision log for full reasoning. Index addition in item 2 makes the future rewrite cheap when it lands.

2. **Date indexes on `Models.swift`.** Add `#Index<HabitEntry>([\.date])` and `#Index<JournalEntry>([\.date])`. Re-creates the `byDateIndex` declarations the original `.xcdatamodeld` had. Lightweight on-launch migration; CloudKit-safe (no `.unique`).

3. **Cold paths — left alone.** `BackupManager`, `JournalPDFGenerator`, `JournalJSONExporter`, `JournalExportView`, `DayJournalView` full-table fetches stay as-is. Rare, async-tolerable, and backup needs full-table by definition.

4. **Dashboard calc — stays on `@MainActor`.** No `ModelActor`. Decisions 1+2 narrow the dashboard fetch enough that the year-view hitch should resolve on its own. If it still hitches after ship, that's a new bead, not a watch-item.

## Validation

- Clean build on iOS + widget targets.
- Today tab: current-day completion renders correctly; tap-toggle persists.
- Widget: timeline reflects state; tap-toggle works + reflects in the app.
- Dashboard: week / month / quarter / year all render with correct streak + completion numbers.
- Existing-store launch: first launch on the new build opens the in-place store with existing habits + entries intact.
- Subjective: year-view Dashboard scroll on the dev device is visibly smoother.

- 2026-05-13 — **Decision 2 correction caught at start of build phase.** Original framing ("habit-id only predicate, date-narrowing in Swift") didn't actually save anything — `habit.entries` already issues "select entries where habit == X" at the SQL layer, so a habit-only predicate fetches the same rows and materializes the same objects. The real win requires date narrowing IN the predicate (so the SQL `WHERE` clause filters before object materialization), which Decision 4's date index makes cheap. Surface revised: predicate goes `entry.habit == habit && entry.date! >= dayStart && entry.date! < dayEnd`. Relationship-equality (`entry.habit == habit`) sidesteps the optional-UUID `#Predicate` fragility flagged in the widget's Wave-3a comment. Remaining bet: `Date?` in `#Predicate` works. Fallback if it doesn't: predicate by date range only across `HabitEntry`, filter habit in Swift (date index keeps it cheap). Scope_files and Decisions 1/3/4 unchanged.
- 2026-05-13 — **Item 1 deferred to `bt-0003`; bead reshaped to ship items 2/3/4 honestly.** Build phase surfaced that the `Date?`-in-`#Predicate` bet was wrong in two ways: (a) `entry.date!` force-unwrap doesn't compile (`ForcedUnwrap` isn't a `StandardPredicateExpression`); (b) `(entry.date ?? sentinel)` nil-coalesce *also* doesn't compile in conjunction with relationship-equality (`NilCoalesce<KeyPath, Value>` in the comparison doesn't reduce when paired with the `Equal<...Optional<Habit>...>` clause). Three predicate shapes attempted, two failed builds. The shape that would work is making `HabitEntry.date` non-optional in `Models.swift` — but that's a SwiftData schema-migration (not lightweight) against a live CloudKit-synced store containing rows the Core Data era wrote with the field as Optional. Code-write paths all currently set a non-nil date (verified: `HabitDataRepository.setCompletion`/`updateEntryDetails`, widget `CompleteHabitIntent`, `BackupManager` restore with `Codable Date` non-optional), but the data-at-rest risk in the synced store is real and the codebase has defensive `entry.date ?? Date()` patterns (`JournalJSONExporter:45`+`73`, the relationship-scan guards) suggesting the original author took it seriously. Two options at that point: (a) expand bt-0004 to include the `Date? → Date` lift + the schema migration, (b) ship the rest of bt-0004 clean and defer the predicate work to `bt-0003`. **Chose (b)** because the `Date?` is one example of the broader Core-Data-mirror legacy-optional pattern that `bt-0003`'s model restructure will fix anyway (likely also `JournalEntry.date`, possibly others) — fixing it once in `bt-0003`'s migration plan is the same work amortized across multiple correctness fixes, instead of a one-off migration here that gets superseded weeks later. Predicate rewrites in `Habits/HabitDataRepository.swift` and `BulletTrackerWidgets/BulletTrackerWidgetsBundle.swift` reverted to their pre-bt-0004 state; date indexes in `Data/Models.swift` kept (items 2/3/4 ship). When `bt-0003` lifts the legacy optionals it inherits a clean target: the indexes are already there, so the predicate rewrite becomes ~50 lines instead of a hundred.
