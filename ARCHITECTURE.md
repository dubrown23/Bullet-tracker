# bullet-tracker — Architecture & Build Reference

## Vision

A quick way to enter data and see it visually — simple, fast, a "quick hit": pop in, tap to log, glance at the patterns. Built for long-term personal tracking, not for other users. Kept deliberately minimal.

Long-term, the plan is to merge this with **Dustin's Health** (dh — the voice-first health logger Dustin already uses for meals). That merge started 2026-10-26 with a settled design (shared note in dustin-system: `memory/in_flight/habits-voice-dh-bullet-2026-10-26.md`): voice lands in dh as day facts + an inbox of actions; **Bullet stays the master copy of habits and holds every grading rule**; dh only reports facts. Step 0 (`bt-0017`) proved the pipeline with fake data; Step 2 (`bt-0018`, 2026-10-27) gave the app the rules it needs before real data arrives — a neutral Rest grade, targets as habit settings, "in progress" today, and hand grades that win over automatic ones until put back on auto, with only the iPhone writing automatic grades. **Step 3 (`bt-0019`, live 2026-10-27) is the real sync:** the iPhone talks to dh's app endpoint with a key kept in its Keychain, sends the habit list, targets and today's taps, pulls changed days, meal and workout facts and the voice inbox, grades with its own rules and confirms back; Diet and Workout are graded from real data from that day forward, and the iPad only shows. **A design pass the same evening (`bt-0021`) made the two graded rows legible:** the Today caption says who set the day (Auto / Set by you / Set by voice) with Back to Auto on the row, and Log Details shows dh's meals and workout sessions from a `health` key kept beside, never inside, the notes. **`bt-0020` (2026-10-28) closed the loop from the tap side:** a hand tap on today sends itself a few seconds later, a burst of taps is one send, leaving the app sends at once, and a tap can never be hidden by the on-open throttle — so "what's left today" by voice is right without a pull-down; still iPhone only. **`bt-0022` (2026-10-28) laid the data for the Dashboard that replaces the dh website** — backup keeps dh's `health` block, steps are stored per day, carbs / fat targets live on Diet, and a one-time rewrite gave every habit a clean start on 2026-10-27 except Poison, with Workout rebuilt from dh's sessions back to Aug 1 — and **`bt-0024` the same evening fixed how a negative habit reads: only slips get marked, and its rate is a slip rate.** **`bt-0023` (shipped 2026-10-29) is that Dashboard:** one day like the website on top — Eaten vs Burned, where burned is Apple Health's active + resting total read by Bullet itself and the sessions' calories are never added to it, a calorie band, three rings, the driver line, meals and training with a warning that is never silent when sessions add up to more than Health's active energy — and the habit trends underneath; a one-time refresh carried dh's corrected session calories onto the stored rows. The dh website dashboard was turned off on 2026-10-29. **`bt-0026` (2026-10-29) remade the Today row as a checklist** once the Dashboard was live: a round control on the left is the one way to mark a day, six quiet dots are the history you look at, the row opens Log Details, and avoidance habits sit in their own Avoiding section — the Reminders shape, chosen from four layouts mocked side by side on the simulator. The app itself was dialed in first (the 2026-10-24/25 Duo + design-language wave) before taking this on.

## Origin

Not pre-planned — started building it, then rewrote it several times; it began as a completely different app, and it evolves as needs change. As of mid-2026 the priority is getting the *foundation* right — the bead / three-doc / skill system, a clean architecture, the patchwork cleaned up — because earlier attempts haven't stuck. Adopted the bead system 2026-05-12.

## Founding decisions

_(Numbered list. Each entry: decision + reasoning. Append-mostly.)_

1. **Migrate the data layer from Core Data to SwiftData** (decided 2026-05-12 — `bt-0001`). The whole persistence layer was hand-rolled Core Data plumbing (`CoreDataManager` / `HabitDataRepository` cache / `HabitCalculationService` with an `@unchecked Sendable` over a stored context). SwiftData is the framework Apple is actively developing for exactly this shape (iOS-only, single-user, CloudKit-synced); moving to it structurally eliminates several patchwork issues rather than patching them (the "three doors into the DB", the cache-thrash, the calc thread-safety hack) and replaces hand-maintained plumbing with first-party code that SDK updates carry forward — which matches Dustin's stated goal of leaning on Apple frameworks under the hood. Two phases: **Phase 1** (`bt-0002`) = swap the engine with the data model *shape* unchanged (so the existing CloudKit store opens in place); **Phase 2** (later bead) = restructure the model — type the `details` JSON blob, collapse the 3-way completion state to one enum, remove the vestigial `JournalEntry` future-log fields. Approach: one focused push on the `swiftdata-migration` branch (a Core-Data/SwiftData coexistence period was considered and rejected as too fragile for a one-person app), JSON backup as the safety net. Full evaluation + rationale in `bt-0001`'s Decision log; build plan in `bt-0002`.

### `bt-0001` (shipped 2026-05-12) — decided the data foundation: migrate to SwiftData, two-phase

**Summary:** decision bead; design pass run this session. Build work → `bt-0002` (Phase 1 — engine swap, model unchanged) + `bt-0003` (Phase 2 — model restructure). Decision-bead deliverable was the direction + a filled Plan, both done.

**Why:**

The entire data layer was hand-rolled Core Data plumbing:
- `CoreDataManager.shared` — `NSPersistentCloudKitContainer`, App Group store, CRUD on Habit/HabitEntry/Collection
- `HabitDataRepository.shared` — `@MainActor @Observable` cache (`habits[]` + `[UUID:[Date:HabitEntry]]`), optimistic UI updates, background-context writes, manual `NSManagedObjectContextDidSave` merge, widget reload
- `HabitCalculationService.shared` — `@unchecked Sendable`, streaks/rates/heatmap, holds its own `viewContext` *and* takes a passed-in context
- Widget extension, `BackupManager`, `JournalPDFGenerator` all touch Core Data directly

iOS-only, single-user, CloudKit-synced — squarely SwiftData's design target. A SwiftData rewrite would delete most of `CoreDataManager`, the manual merge dance, the optimistic-update bookkeeping, the save-notification listener, and the `@unchecked Sendable` hack.

Real migration with real risk: the `.xcdatamodeld` becomes `@Model` types (existing-store migration needs care), the widget gets rewritten against `ModelContainer`, the JSON backup format must stay round-trip-compatible, and CloudKit-via-SwiftData has its own constraints. The model was mid-cleanup (the `JournalEntry` future-log fields, the dual `completed`/`completionState`, the `details` JSON blob) — a migration was the natural moment to fix those, which made it bigger but more worthwhile.

This bead was the **decision**, not the work. Downstream patchwork items deferred until settled: "three doors into the database" → one owner; `details` JSON blob → typed; 3-way completion state → `CompletionStyle` enum; `HabitDataRepository` cache-thrash; `HabitCalculationService` thread-safety.

**Plan locked at decision (two phases):**

- **Phase 1** — swap the engine, model shape unchanged. Convert the 6 entities (`Habit`, `HabitEntry`, `JournalEntry`, `Collection`, `Note`, `Tag`) to SwiftData `@Model` types field-for-field identical to the existing `.xcdatamodeld`, so SwiftData opens the existing App-Group / CloudKit SQLite store with no data restructuring. Delete most of `CoreDataManager` + `HabitDataRepository` cache + the merge listener; stand up `ModelContainer` with `cloudKitDatabase: .automatic`; rewrite widget + `BackupManager` consumers; fold in flag #4 (kill name-keyword workout detection). Highest risk: first launch opening the existing synced store with the new schema. Mitigation: JSON backup fallback. → became `bt-0002`.
- **Phase 2** — clean the model (separate bead, after Phase 1 ships + stabilizes). `details` JSON-string → typed; collapse 3-way completion state to one enum; remove vestigial `JournalEntry` future-log fields (blocked on the #9 Journal-intent question). → became `bt-0003`.
- **Independent of this chain (anytime):** Flag #5 repo-layout cleanup.

**Decision log:**
- 2026-05-12 — created, queued. Surfaced during the 2026-05-12 fresh-eyes architecture review (flag #6 of 9). Holds the data-foundation decision; Plan stays TBD until a design pass. Flags #1/#2/#3/#7/#8 noted as downstream of this decision.
- 2026-05-12 — design pass run; **decided: migrate to SwiftData, two-phase**. Rationale: SwiftData structurally *eliminates* flags #1/#7/#8 rather than patching them; moves the one remaining old-stack layer onto the framework Apple is actively developing (less hand-rolled code to own, SDK updates carry it forward — matches Dustin's "rely on Apple under the hood" goal); migration risk to existing synced data is real but reducible via the two-phase split + the JSON-backup fallback. Downstream flag routing locked: #1/#7/#8 → Phase 1; #2/#3 + Journal-fields half of #9 → Phase 2; #4 → folded into Phase 1; #5 → still independent.
- 2026-05-12 — **shipped** (deliverable = the decided direction + filled Plan, both done). Build work lives in `bt-0002` (Phase 1) + `bt-0003` (Phase 2). This entry is now the permanent decision record.

### `bt-0004` (shipped 2026-05-13) — SwiftData data-layer perf pass: indexes-only ship; predicate rewrite deferred to `bt-0003`

**Summary:** Original 4-decision Plan was (1) hot-path predicate rewrite, (2) date indexes, (3) cold paths untouched, (4) no `ModelActor`. Build phase surfaced that SwiftData's `#Predicate` on this iOS version rejects every shape of optional-`Date` comparison tried (force-unwrap, inline nil-coalesce, captured-local sentinel) — `Date?` would need to become `Date`, which requires a SwiftData `VersionedSchema` migration against the live CloudKit-synced store. That belongs in `bt-0003`'s model-restructure surface, not as a one-off scope expansion here. **Net shipped:** two `#Index` lines in `Data/Models.swift` (`HabitEntry.date` + `JournalEntry.date`) — re-creates the `byDateIndex` fetch index the original `.xcdatamodeld` had, making any future date-filtered query cheap (including `bt-0003`'s eventual predicate rewrite).

**Why:** `bt-0002` Phase 1 swapped the data engine but left two known perf shortcuts in place: (d) dashboard aggregation on `@MainActor` (fine at current sizes, can hitch on year view), and (e) `HabitStore` reads filter `habit.entries` in memory (hundreds-to-thousands of objects faulted per habit per Today render). Both in `bt-0002`'s Decision log. Pure perf work, no behavior change, no model-shape changes — that's why this is its own bead and not folded into `bt-0003` (where model shape *does* change).

**Plan:** four targeted changes — (1) hot-path predicate rewrite (3 `HabitStore` reads + 2 widget reads → `FetchDescriptor` + `#Predicate` on `habit.id` + date range + fetch limit), (2) date indexes on `Models.swift` (`#Index<HabitEntry>([\.date])` + `#Index<JournalEntry>([\.date])`), (3) cold paths left alone (`BackupManager`, Journal exporters, `DayJournalView` — rare, async-tolerable, full-table by design), (4) dashboard calc stays on `@MainActor` (decisions 1+2 should narrow fetches enough).

**Decision log:**
- 2026-05-13 — created from `bt-0002` ship. Routed here rather than folded into `bt-0003` because Phase 2 was blocked on the #9 Journal-intent question (may sit for weeks); perf is purely additive and shouldn't gate on that. Tradeoff accepted: two trips to the data layer instead of one.
- 2026-05-13 — design pass + activation. Predicate scope: hot path only. Predicate shape: habit-id only, date in Swift (sidesteps optional-`Date` `#Predicate` fragility). Indexes: re-add `byDateIndex`-equivalents. No `ModelActor`. `scope_files` locked to 3 files; status `queued` → `in_progress`.
- 2026-05-13 — Decision 2 correction caught at start of build. Original "habit-id only, date narrowing in Swift" didn't save anything — `habit.entries` already issues "WHERE habit == X" at SQL layer, fetching the same rows. Real win requires date narrowing IN the predicate. Revised: `entry.habit == habit && entry.date! >= dayStart && entry.date! < dayEnd`. Relationship-equality sidesteps optional-UUID fragility. Remaining bet: `Date?` in `#Predicate` works.
- 2026-05-13 — Item 1 deferred to `bt-0003`. Build surfaced that `Date?`-in-`#Predicate` bet was wrong: (a) `entry.date!` force-unwrap doesn't reduce to `StandardPredicateExpression`; (b) `(entry.date ?? sentinel)` nil-coalesce doesn't reduce either. ### `bt-0003` (shipped 2026-05-13) — SwiftData Phase 2: model restructure + drop dormant journal machinery

**Summary:** Phase 2 of the SwiftData migration — model itself cleaned up. **Eight waves** (0 / 1 / Recovery / 2 / 3 / 3.5 / 4 / 4.5 / 5) on `swiftdata-phase2` branch, merged to `main` at ship. **Five deliverables landed:** (1) dropped dormant journal machinery (`Collection` / `JournalEntry` / `Tag` `@Model` types + 7 vestigial future-log fields + backup mirrors + half-built collection UI — Wave 1, −259 lines); (2) lifted `HabitEntry.date: Date? → Date` non-optional (Wave 2; default `.distantPast` syntactic sentinel; `init` requires explicit date); (3) collapsed 3-way completion state — added `CompletionStyle` + `DetailKind` enums on `Habit`, replaced `completed: Bool` + `completionState: Int16` with typed `CompletionState` on `HabitEntry` (Wave 2); (4) typed the `details` JSON blob — `HabitEntryDetails` discriminated enum exposed as a computed property over a stored `detailsJSON: String?` column after Wave 3.5 SwiftData rejection of `Codable`-enum-as-attribute (same `bt-0004` fragility class); (5) rewrote 5 hot-path predicate reads (the deferred `bt-0004` perf work) with the non-optional date unblocking it, +66 lines + Wave 4.5 Today-card N+1 hotfix +24 lines. Migration vehicle was **Path 3 (wipe + restore via `BackupManager`)** — proven during Wave 1 recovery from a schema-shrink + CloudKit `HistoryExpired` interaction; Wave 5 ship re-ran the same cycle cleanly end-to-end.

**Why:** `bt-0001` decided two-phase. `bt-0002` shipped Phase 1 (engine swap, model unchanged). Phase 2 cleans the model.
